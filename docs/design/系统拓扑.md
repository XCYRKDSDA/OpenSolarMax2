# 术语

- 下文严格区分“状态”与“组件”：
  - “状态”指描述世界的任意一个值，比如某个实体的 $x$ 坐标；
  - “组件”指 ECS 框架中的 Component，它是状态的承载体，但与状态并不等价。

- 下文严格使用“上一帧”与“这一帧”：
  - 把执行某次更新之前世界中的所有状态，称为“上一帧”的状态；
  - 把执行该次更新之后的所有状态，称为“这一帧”的状态。

# 原理

- 我们把状态分为两大类：
  - 时变状态：随时间积分而变的状态，比如由速度项驱动的位置；
  - 随动状态：不随时间积分、而是直接由其他时变状态或随动状态计算出来的状态，比如由相对位姿和父子关系计算出的绝对位姿。

- 因此，执行计算更新的系统也分为两大类：
  - 积分系统：按欧拉前向积分，根据上一帧状态和时间，计算这一帧状态的系统；
  - 随动系统：根据这一帧的某些状态，计算这一帧另一些状态的系统。

- 受计算机架构限制，所有系统必须按某个先后顺序执行。系统间的执行顺序本质上取决于每个系统想读取哪些时刻的哪些状态、又要写入哪些状态：写入状态 $x_n$ 的系统，不应先于读取状态 $x_{n-1}$ 的系统执行。汇总所有系统对状态的读写，我们期望系统整体能构成一张有向无环图，将其拓扑排序后即可执行。

- 但随动系统中可能存在读写环路，例如：
  - 某个系统既读取某个状态，又根据其值写入某个状态。例如：状态机状态切换系统读取当前状态，判断切换条件是否满足，满足后切换状态；
  - 系统 A 读取状态 T，根据其写入状态 U；系统 B 读取状态 U，根据其写入状态 T。例如：系统 A 根据相对位姿计算绝对位姿，系统 B 根据绝对位姿创建相对位姿关系。

- 参与环形结构的系统需要不断执行，直到收敛，其形态类似不动点迭代，即 $x \leftarrow f(x)$，最终收敛到 $x = f(x)$。而对互相耦合的不动点迭代 $x \leftarrow f(x,y),\ y \leftarrow g(x,y)$，不应当分别收敛，应当合并在一起统一收敛：$x,y \leftarrow h(x,y)$。

- 因此我们在随动系统中引入不动点迭代：
  - 挑选“环”中至少一条边，将其上的操作延迟，从而打破环路，使拓扑排序能够正常进行；
  - 待所有随动系统的立即操作都执行完毕后，检查是否存在延迟操作；
  - 若有，说明不动点迭代尚未收敛，一次性播放所有延迟操作，继续循环；
  - 若没有，则不动点迭代完成，结束循环。

- 由于游戏是高实时性的系统，循环会导致每一帧计算时间不确定。为了降低影响面，我们要找出尽可能少的参与不动点迭代的系统，降低迭代的体量。任何一组随动系统，可以拆解为如下结构 $y \leftarrow f(x),\ y \leftarrow g(y,x),\ z \leftarrow h(y,x)$，其中将只有 $g$ 参与不动点迭代。

# 实现

## 声明积分系统与随动系统

- 积分系统必须声明 `[Update]`，并实现 `ITickSystem` 接口；

- 随动系统必须声明 `[LateUpdate]`，并实现 `ICalcSystem` 或 `IDelayedCalcSystem` 接口。后者的 `Update()` 会额外收到一个 `CommandBuffer` 对象，用于缓存延迟操作。

## 声明立即读写属性

要让系统间的执行顺序可以推导，又要避免中心式地显式声明所有顺序，我们使用读写标签声明每个系统对状态的读写，框架据此推导系统间的拓扑关系：

- 积分系统使用 `[ReadPrev(T)]` 声明自己读取上一帧 `T` 类型组件的值，使用 `[Tick(T)]` 声明自己对 `T` 类型组件进行积分；

- 随动系统使用 `[ReadCurr(T)]` 声明自己读取这一帧 `T` 类型组件的值，使用 `[Calc(T)]` 声明自己计算并写入这一帧 `T` 类型组件的值。

- 读写标签的组件可以写 `typeof(AllComponents)` 作为通配，表示该访问声明对所有组件成立：`[Calc(typeof(AllComponents))]` 的系统视为写入所有组件类型。目前这一通配符只作为特例开放给 `ApplyAnimationSystem` 一个系统。

## 声明显式顺序

读写标签以组件类型为粒度，并不精确：同为 `T` 类型的组件实际对应多个不同的状态，标签无法区分一个系统读/写的是这个实体的 `T` 还是那个实体的 `T`。因此，多个系统写入同一类型组件的情形必然出现。框架要求开发者必须为它们显式声明先后关系：

- `[ExecuteBefore/After(系统类型, 原因, 组件类型)]`：显式声明当前系统先于/晚于另一个系统执行，需给出原因并指定起作用的组件类型。所列的每个组件类型都必须被两个系统写入。

- `[FineWith(系统类型, 原因, 组件类型)]`：显式声明当前系统与另一个系统的执行先后无关，需给出原因并指定起作用的组件类型。所列的每个组件类型都必须被两个系统写入。

  > 上述两类顺序标签中禁止使用 `AllComponents` 通配。

- `[Priority(n)]`：声明系统整体优先级，数值大的靠后执行。但优先级不能抵消读写的顺序：若读写顺序与优先级顺序相反，拓扑图中会成环，框架会拒绝运行。

## 延迟操作与不动点循环

- `[DelayedCalc]` 声明随动系统会进行延迟操作。这样的系统必须实现 `IDelayedCalcSystem`，并把延迟操作写入 `Update()` 传入的 `CommandBuffer` 缓存。

  - 除了显式的 $x \leftarrow f(x)$ 环状结构外，结构化变更也是一种环：框架采取扩展性设计，当一个系统创建或销毁实体时，它并不清楚该实体包含哪些组件。因此我们使用有罪推定，认为新建或销毁的实体包含任意可能的组件类型。

  - 考虑到上述情况，`[DelayedCalc]` 没有提供声明组件类型的入口：延迟操作的组件类型已不可能在实际运行前就确认并参与排序。

- 我们将随动系统进一步分为三个子类：

  - $*\leftarrow f(x,y)$：发生延迟操作的系统。$*$ 代表任意状态。

  - $y \leftarrow g(x)$：普通随动系统，但其输出是第一类的输入，因此参与了环路，被囊括进不动点迭代循环。

  - $z \leftarrow h(*)$：普通随动系统，但其输出不是第一类的输入，因此不参与环路，在不动点迭代循环之后执行。

  上述三类中，前两类需要参与不动点循环。

- 每帧更新时，框架会先执行全部积分系统，再进入不动点循环。框架会反复执行前两类参与迭代的随动系统，每一轮结束后，若存在延迟操作，则统一播放后继续迭代，直至某轮没有任何延迟操作即判定为收敛；收敛后执行第三类不参与迭代的随动系统。

- 不动点循环设 32 轮上限，超限抛异常，作为不收敛时的保险。

## 响应式系统与双缓冲

- 框架允许开发者定义响应式系统。这类系统只响应延迟执行的 Arch 事件，不参与拓扑排序，也没有 `Update()` 方法。框架要求这类系统使用 `[Reactive]` 标记，并实现 `IReactiveSystem` 接口。

- 响应式系统响应事件时，还可能继续添加延迟操作，这些操作同样要进入不动点循环播放。为此，框架采用双缓冲方案：播放一个缓冲期间由事件回调等产生的新延迟操作落入另一缓冲。框架反复播放两个缓冲，让事件不断触发，直至不再有任何新增延迟操作。这一循环也设 32 轮上限。
