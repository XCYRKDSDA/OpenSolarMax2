# 工作流：spec-first

1. 确定测试内容对应的 spec。直接向用户索要 spec，或按 to-spec SKILL 描述已实现的功能提供的能力，并向用户讨论确认。该 spec 可临时落盘。
2. 规格确认后，严格按照规格实现测试，测试代码要不多不少地精准表达规格，不测试任何规格未许诺的能力。
3. 把规格以注释形式整理进入测试代码文件头（可不保留原始格式），使得其结合测试代码本身后，足够精准地描述规格。
4. 如果之前 spec 落盘了，则移除临时文件，因为其规格内容已经完全由测试代码表达。

# 目录组织

- 所有测试项目平铺位于仓库 tests/ 目录下。
- 一个测试项目只负责测试一个被测项目。
- 若被测项目名为 Foo.Bar，则测试项目命名为 Foo.Bar.Tests，位于 tests/Foo.Bar.Tests/ 下。
- 由数据驱动的测试的数据文件按照各个测试类和各个用例，放在各个测试项目的 TestData/<测试类>/<测试用例> 目录下。

# 测试边界

- 测试对且只对规格负责。测试的期望值、形式、顺序等一切细节只应来自规格，不允许对着实现写测试。
- 只通过预先与用户确认的公开接口测试。不碰内部成员，不通过反射获取私有对象，不在测试里复刻被测逻辑。
- 不测第三方库行为，即使它们是 fork 且自行修改的。第三方库的行为由第三方库自己的测试保证。

# 测试写法

- 结构重复的测试用例优先使用数据驱动，而不是在代码中反复编写大量重复测试代码。
- 测试类的名称需要精确地概括被测功能，不得更泛、不得更窄。名词形式，并加 Test 后缀。
- 测试用例的名称需要精确地概括被测功能的被测行为，不得更泛、不得更窄。默认省略作为主语的被测对象，以动宾结构概括被测行为。
- 辅助工具默认归使用它的测试文件所有，确认被复用后再抽取到独立文件或项目。
- 测试代码文件头讲且只讲两件事：对被测功能的展开介绍，和测试用例所覆盖的行为规格。行为规格用无序列表，一条一类。上述「展开」比测试类名、测试用例名更详细，但也无需面面俱到长篇大论。

    ```
    // <被测功能中文简述>
    //
    // <被测功能展开介绍>
    //
    // - <行为规格>
    ```

# 其他代码规范

- 上游、父类代码只注释自身契约，下游、子类的具体实现由其自身注释。
- 只注释「做了什么」，禁止注释「没做什么」。
- 代码注释只补充本文档未规定的本地细节。
- 被调用代码块放在调用它的代码块的前边，以保证线性的阅读体验。
- 函数名与功能严格一致：名字声称会做的必须做到，只是选择性做的不得在名字里声称必做。
